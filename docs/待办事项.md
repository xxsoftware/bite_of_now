# 待办事项（新需求 & 待修复问题）

> 本文档用于记录产品评审中发现的新需求、待确认方案及已知问题。
> 按优先级排序（P0→P1→P2→P3），同优先级内按序号排列。完成后可标记删除线或移至"已完成"。

---

## 优先级说明

| 优先级 | 定义 | 判断标准 |
|--------|------|---------|
| **P0** | 核心阻塞 | 影响推荐准确性、性能指标或已承诺的功能改造 |
| **P1** | 重要体验 | 用户高频使用、显著影响满意度、实现成本适中 |
| **P2** | 体验优化 | 锦上添花、使用频率中等、可延后 |
| **P3** | 长期规划 | 架构重构、影响面大、需更多调研 |

## P0 - 核心阻塞（4 项）

### P0-1 时令系统增强：地区选择与时令校验
- **来源**: PRD 评审 - 问题1 | **状态**: ✅ 已完成
- **为什么 P0**: 时令是推荐系统的"强约束"基础。当前依赖系统时间，未考虑地区差异和时间篡改，出错则整个推荐崩塌。
- **方案**:
  1. App 初始化时自动检测/引导用户选择所在地区（中国默认）。
  2. 设置页新增"地区与时令"选项，允许手动校准当前时令。
  3. 时令数据按地区分离存储（如 `season_cn.json`、`season_au.json`）。
  4. 增加"时令校验"机制：当检测到系统时间突变超过 7 天时，弹窗提示用户确认。
- **涉及模块**: 设置页、首页推荐、数据库（新增地区配置字段）

### P0-2 AI 推荐按日缓存
- **来源**: PRD 评审 - 问题12 | **状态**: ✅ 已完成
- **为什么 P0**: PRD 要求冷启动 < 2 秒。当前每次打开都请求 AI，响应时间不可控，必然超标。缓存是满足性能指标的必要手段。
- **方案**:
  1. 推荐结果按日期缓存到 SQLite（复用 `daily_recommendation` 表）。
  2. 同一天内进入首页直接读缓存，不再请求 AI。
  3. 用户点击"重新生成"或日期切换时才触发新请求。
  4. "换一换"只刷新单道菜，不影响其他三餐缓存。
- **涉及模块**: 首页推荐、AI 推荐逻辑（`src/lib/ai.ts`）、数据库

### P0-3 视频方案改造：保留 Plyr，扩展为多平台适配播放器
- **来源**: PRD 评审 - 问题6 | **状态**: ✅ 已完成
- **为什么 P0**: 用户已明确决定废弃当前本地视频方案，改为在线视频。这是已承诺的改造，阻塞视频相关功能的继续开发。
- **方案**:

  `VideoPlayer` 组件根据 `platform` 字段智能分发：

  | 平台 | 播放方式 | 说明 |
  |------|---------|------|
  | **YouTube** | Plyr 原生 | `data-plyr-provider="youtube"`，享受 Plyr UI 统一主题 |
  | **本地视频** | Plyr HTML5 | `<video>` 标签，Plyr 接管控制栏 |
  | **B站** | iframe 嵌入 | `player.bilibili.com/player.html?bvid={id}&danmaku=0&autoplay=0` |
  | **抖音** | iframe 嵌入 | `open.douyin.com/player/video?vid={id}&autoplay=0`，竖版展示 |

  1. 编辑页支持粘贴多平台链接（B站/抖音/YouTube）。
  2. 前端自动解析链接提取平台类型和视频 ID（短链接需网络跳转解析）。
  3. 数据库存储：`video` 字段存储 `{ platform, videoId, originalUrl, embedUrl }`。
  4. 离线时视频模式自动不可用，降级为图文模式。
  5. iframe 加载失败时显示"视频可能已下架或不可用"。
- **涉及模块**: VideoPlayer 组件（扩展）、RecipeForm 编辑页、RecipeDetail 详情页、数据库

### P0-4 AI 推荐"不喜欢"反馈的时效与衰减机制
- **来源**: PRD 评审 - 问题2 | **状态**: ✅ 已完成
- **为什么 P0**: 推荐系统的核心反馈闭环。没有时效机制，推荐池会越来越窄，最终可能无菜可推。
- **方案**:
  1. 引入"软性不喜欢"机制：默认 7 天后自动衰减解除。
  2. 设置页新增"口味黑名单"管理入口，支持查看、清空、删除误操作条目。
  3. 长期多次（3 次以上）被"换一换"的菜品升级为"硬拉黑"（30 天）。
  4. 支持"撤销"误点的"换一换"。
  5. "不喜欢"可针对整道菜，也可细化到维度（做法、口味等）。
- **涉及模块**: 设置页、首页推荐、数据库（`disliked_recipes` 表扩展字段）

## P1 - 重要体验（6 项）

### P1-5 AI 推荐解释性与"不太对"微调反馈
- **来源**: PRD 评审 - 问题4 | **状态**: ✅ 已完成
- **为什么 P1**: 可解释性是 AI 产品从"玩具"变为"工具"的分水岭。用户信任推荐后，"换一换"使用率会自然下降。
- **方案**:
  1. 推荐卡片标签下方新增小字"推荐理由"，从时令/轮换/目标/避讳 4 个维度中选最相关的 1-2 条展示。
  2. "换一换"旁增加"不太对"按钮，弹出微调选项（更清淡/更辣/换个食材/换个做法）。
  3. 微调反馈写入下一次推荐的 Prompt，形成闭环优化。
- **涉及模块**: 首页推荐卡片、AI Prompt 组装逻辑

### P1-6 统一 Toast 操作反馈系统
- **来源**: PRD 评审 - 问题13 | **状态**: ✅ 已完成
- **为什么 P1**: 操作反馈是 UI 的基础礼仪。没有反馈会让用户产生不确定感，实现成本低但覆盖全 App 80% 交互场景。
- **方案**:
  1. 轻量 Toast 组件（CSS + React Portal，无需额外库）。
  2. 覆盖核心操作：成功（"已加入购物清单"/"打卡成功"/"已收藏"/"导出成功"）、失败（"操作失败，请重试"/"网络异常"）。
  3. 位置：顶部居中，2 秒后自动消失，不打断用户操作。
- **涉及模块**: 全局组件、各页面交互点

### P1-7 本地回退算法体验优化
- **来源**: PRD 评审 - 问题5 | **状态**: ✅ 已完成
- **为什么 P1**: 离线体验与在线体验的落差会直接影响用户对 App 的整体评价。当前 macros 固定 45/25/30，与身体目标不匹配。
- **方案**:
  1. 本地回退根据用户身体目标动态调整 macros 比例（减脂/增肌/维持不同配比）。
  2. 首页顶部用轻量提示条显示当前推荐模式（"AI 智能推荐" / "本地推荐"）。
  3. 本地模式时小字提示"配置 API Key 获得更个性化推荐"。
  4. 连续使用本地推荐 3 天后，设置页入口出现小红点引导配置。
- **涉及模块**: 首页、AI 推荐逻辑（`src/lib/ai.ts`）、设置页

### P1-8 菜谱评分与收藏
- **来源**: PRD 评审 - 问题7 | **状态**: ✅ 已完成
- **为什么 P1**: 评分数据是推荐算法的金矿，知道用户"喜欢"什么比"吃了"什么更有价值。且实现轻量。
- **方案**:
  1. 菜谱详情页新增"收藏"心形按钮。
  2. 饮食记录打卡时，弹出可选的"这道菜怎么样？"评价（1-5 星，一步完成，可跳过）。
  3. 评分数据写入数据库，AI Prompt 中增加"用户高评分菜品列表"作为正向偏好参考。
- **涉及模块**: RecipeDetail 详情页、DietRecords 打卡流程、数据库、AI Prompt 组装

### P1-9 食谱删除级联处理
- **来源**: PRD 评审 - 问题14 | **状态**: ✅ 已完成
- **为什么 P1**: 数据完整性是应用稳定性的底线。删除导致页面白屏或数据错乱，用户会立刻失去信任。
- **方案**:
  1. 删除前弹窗确认，提示"该菜谱相关的 XX 条饮食记录将保留"。
  2. 饮食记录不级联删除，`recipe_id` 改为 nullable，显示时回退为菜品名称文字。
  3. 购物清单中来自该菜谱的未购买项自动删除（已购买的不影响）。
  4. 如果该菜谱在今日推荐缓存中，自动刷新推荐。
- **涉及模块**: 删除逻辑、数据库 schema、DietRecords 显示逻辑、ShoppingList 清理逻辑

### P1-10 导出时跳过 API Key 字段
- **来源**: PRD 评审 - 问题11 | **状态**: ✅ 已完成
- **为什么 P1**: 产品核心卖点是"绝对隐私安全"。如果用户通过分享备份无意泄露 API Key，卖点变讽刺。
- **方案**: 数据导出 JSON 时，`aiConfig` 字段完全跳过 `apiKey`（不导出）。用户恢复备份后需重新输入 API Key。
- **涉及模块**: 数据导出逻辑（`src/lib/db.ts` 或设置页导出功能）

## P2 - 体验优化（4 项）

### P2-11 饮食记录数据洞察——周报功能
- **来源**: PRD 评审 - 问题3 | **状态**: 方案已确认，待开发
- **为什么 P2**: 记录类工具的最大死因是"记录变得毫无意义"。周报让用户感到"记录有价值"。但用户并非每天查看，频率较低。
- **方案**:
  1. 在饮食记录页新增"周报"入口。
  2. 每周日晚 8 点推送回顾通知（系统支持的前提下）。
  3. 核心展示 3 个指标：① 本周营养达标率 ② 菜系多样性评分 ③ 时令达成度。
  4. 不做复杂图表，先展示 3 个清晰数字 + 一句人话建议。
- **涉及模块**: 饮食记录页、数据库（统计查询）、通知系统

### P2-12 购物清单交互优化
- **来源**: PRD 评审 - 问题8 | **状态**: 方案已确认，待开发
- **为什么 P2**: 高频使用的购物清单体验优化，但当前功能可用，优化是增量提升而非阻塞。
- **方案**:
  1. 已勾选食材自动下沉到分类底部（或折叠成"已完成"区域）。
  2. 新增食材时自动归入对应分类（复用 `smartCategory.ts`），无需手动选择。
  3. ~~自定义超市布局~~（太重，暂不做）。
- **涉及模块**: ShoppingList 页面、`smartCategory.ts`

### P2-13 自定义今日菜单与特殊日期标记
- **来源**: PRD 评审 - 问题9 | **状态**: 方案已确认，待开发
- **为什么 P2**: 给用户选择权能提升信任感，但"不需要推荐"的场景使用频率不高。
- **方案**:
  1. 首页推荐卡片区域增加"今天我自己安排"按钮。
  2. 点击后今日三餐变为可编辑状态（从食谱库自选），AI 推荐暂停一天。
  3. 饮食记录页支持对某天标记"外出/聚餐/断食"等特殊状态，不参与推荐和统计。
- **涉及模块**: 首页推荐、饮食记录页、数据库

### P2-14 React Error Boundary 错误边界
- **来源**: PRD 评审 - 问题15 | **状态**: 方案已确认，待开发
- **为什么 P2**: 防御性措施，发生概率低。但如果发生，能防止整个 App 白屏，属于"有备无患"。
- **方案**:
  1. 每个主要页面路由包裹独立 Error Boundary，单个页面崩溃不影响其他页面。
  2. 全局最外层兜底，显示"应用遇到错误"并提供"清除缓存重启"紧急按钮。
  3. Error Boundary 中将错误信息记录到本地日志，方便排查。
- **涉及模块**: 全局路由配置、错误边界组件、日志模块

## P3 - 长期规划（4 项）

### P3-A 多人/家庭饮食场景
- **来源**: PRD 评审 - 问题5
- **问题**: 当前所有偏好都是单用户维度。家庭共用场景下推荐基于谁的偏好？
- **判断**: 涉及用户系统重构，影响面大，暂列为长期规划。

### P3-B 饮食记录社交分享
- **问题**: 用户是否想分享饮食打卡？（生成精美卡片分享到朋友圈）
- **判断**: 锦上添花，非核心功能，暂列低优先级。

### P3-C 图片存储架构优化（base64 → 文件系统）
- **问题**: 当前封面图以 base64 存 SQLite，100 张图 = 200MB+，会导致数据库膨胀、查询慢、备份文件过大。
- **判断**: 用户确认"暂时不用做"，列为长期技术债务。当用户量和图片量增长后再评估。

### P3-D 食材库存管理
- **问题**: 购物清单解决"买什么"，但冰箱库存如何管理？是否支持扫描小票自动录入？
- **判断**: 功能边界容易无限扩大（变成冰箱管理 App），暂列低优先级。
